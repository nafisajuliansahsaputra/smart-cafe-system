# M6: Runtime image SBOM and unsigned CI evidence

## Scope

The existing Docker runtime image CVE scan GitHub Actions workflow builds
two application runtime images (Spring Boot API and standalone Next.js web).
It still blocks fixable HIGH/CRITICAL Trivy findings, and now separately
produces a CycloneDX JSON software bill of materials for **the same local
runtime image**. The PR head SHA (rather than the synthetic pull request
merge commit) is checked out and verified before build. There is no
registry push, deployment or release signature.

Each API and web matrix job uploads a short-lived review artifact named
runtime-sbom-<component>-<source SHA> with exactly:

- runtime-image.cdx.json: CycloneDX inventory generated by Trivy v0.76.1.
- runtime-sbom-evidence.json: unsigned manifest with the exact checkout
  SHA, local image tag and Docker image ID, Dockerfile path and SHA-256,
  SBOM SHA-256, format/version and number of inventoried components.

The scripts/verify-image-sbom.mjs validator fails closed on invalid/truncated or
empty inventory, source/tag mismatch, unexpected component/Dockerfile and
missing Docker image ID. Synthetic negative tests run in the image workflow.
The manifest and BOM are uploaded **only if the CVE and SBOM gates pass**.
Artifacts expire after seven days. No secret-bearing Docker inspect output,
raw application environment or Trivy vulnerability JSON is uploaded.

## Review and limitations

1. Open the corresponding successful PR check, then download the two
   CI artifacts from GitHub Actions.
2. Confirm source SHA and component are correct and match the PR head.
3. Recompute sha256sum runtime-image.cdx.json and compare it with
   sbomSha256 in the companion evidence manifest. Review the components
   list and componentCount before adopting any license or vulnerability
   conclusions. Only runtime packages detected by Trivy are represented.
4. Compare the manifest's dockerfileSha256 with the exact source commit.
   The local image ID is a *local content identifier*, **not an OCI registry
   digest**. The two are not interchangeable.
5. This is **unsigned**, not SLSA provenance, OCI signing, a trusted
   release attestation, or a guarantee that a future separately built
   production image has identical bytes. CI images are never published.
   Future authorized production work must build once, pin and publish an
   immutable registry digest, create signed SBOM/provenance attestations,
   verify signatures before deploy and retain evidence in a governed store.

Production blockers remain: branch protections and review, isolated hosted
staging, TLS, unique secrets, backup/PITR, monitoring, real merchant
integrations, receipt provider and operational sign-off.
